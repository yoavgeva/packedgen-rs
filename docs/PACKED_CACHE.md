# PackedCache: compact arbitrary-value cache

Date: 2026-08-17

`PackedCache<V>` is an experimental concurrent cache built on PackedGen's
adaptive mixed-key index. The redesign removes the per-entry `Arc` that erased
the index's density advantage. It now uses one epoch-reclaimed allocation per
value, compact metadata, and a structure-of-arrays slot directory.

`DirectPackedCache<V>` is the newer pointer-indexed variant. It removes the
generational slot directory, stores one protected entry pointer directly in
the adaptive index, and packs weight, expiry, and CLOCK state into one atomic
word. On the current one-million-entry fixture it uses 21.4% less total
requested RAM and 41.0% less non-payload overhead than the strongest inline
Papaya control. The original Arc-wrapped comparison overstated the total
reduction at 33.4%. The first inline operation and tail-latency reruns are in
`CACHE_PROOF.md`; pinned Linux confirmation remains required.

## Current architecture

1. `LockFreeAtomicU64GenerationMap` stores each exact binary key and one packed
   63-bit arena handle. Keys are not duplicated in the value arena.
2. The handle contains a 24-bit slot, 8-bit arena partition, and 31-bit
   generation. A stale handle cannot observe a recycled slot.
3. Each live value is one `Box<ArenaEntry<V>>`, published through an atomic
   pointer and reclaimed through `seize` epochs. There is no per-entry `Arc`.
4. Slot pointers and generation/access words are separate dense arrays. Stable,
   lazily initialized block directories replace reference-counted block-vector
   snapshots; blocks never move or disappear while the cache is alive.
5. `ArenaEntry<V>` contains `V`, a compact `u32` weight, and a compact atomic
   `u32` expiration tick. The access bit shares the generation word.
6. Reads are lock-free. Fresh slots use population-adaptive atomic bump
   allocation; recycled slots retain partition locks for their free lists.
   Same-key mutations use 2,048 compact striped locks; unrelated keys can be
   written concurrently.
7. Existing-key replacement keeps the same handle and atomically publishes a
   new value pointer. New-key admission uses the index's fused
   `get_or_insert`; a speculative arena value is retired if another writer won.

Unsafe code is confined to `src/cache_arena.rs`. Its boundary protects atomic
pointers before dereference, retires only pointers removed from publication,
keeps the collector alive as long as an owned guard, and drops the epoch guard
before the final collector reference. The rest of the crate remains under the
workspace unsafe-code denial lint.

The direct variant enters its native three-epoch quiescent-state reader before
dereferencing an index pointer. Replacement and removal retain that reader
until the exact pointer is unpublished and queued for reclamation. Bulk-loaded
and newly admitted entries occupy reusable 256-slot partitioned blocks; known
replacement candidates remain individually boxed. Both representations contain
only `V` and one atomic metadata word and share one tagged-pointer index.
Reusable `DirectCacheGuard` reads return borrowed values; owned
`DirectCacheValue` guards remain valid after replacement, removal, or cache
drop. Read-only guards acquire the arena epoch lazily and do not reserve an
index generation. The first guarded conditional admission or admission batch
acquires that reservation only when needed, and `refresh()` advances
initialized guards. Direct expiry uses 31-bit 100 ms ticks, about 6.8 years
from creation.

Frozen reads now retain two independently randomized portable Rapidhash lanes, so
writer routing and PtrHash indexing share one carried 128-bit context instead
of rescanning the key with a second hashing algorithm. Compact overlay bucket
selection uses multiply-high reduction rather than integer division. A
per-generation one-way flag also lets a frozen miss skip the writable overlay
until its first possible write. When the overlay must be consulted, one fused
probe now returns both a matching cell and the empty-slot proof that stops
overflow lookup; misses no longer rescan the same control words. The flag and
hash state are fixed map overhead, not per-entry metadata.

## Read and write APIs

- `pin()` returns a reusable thread-local `CacheGuard`. `guard.get()` borrows a
  value without allocating a guard for every read. Long-running workers should
  call `refresh()` periodically so retired values can be reclaimed.
- `DirectCacheGuard` caches its current-generation publication handle and a
  stable base snapshot. Every lookup still validates the single authoritative
  generation pointer. A transitional predecessor is refreshed as soon as its
  key stripe enables direct frozen-base mutation, so rebuilds cannot leave a
  reader on stale handles. This is worker-local state and adds no bytes per
  resident entry.
- With the opt-in `prepared-keys` feature, callers can prepare only their known
  hot keys and use `guard.get_prepared*()`, prepared insert/replace, discard
  removal, and touch. Each caller-owned handle is 16 bytes: it keeps the full
  64-bit base identity and packs the 11-bit writer stripe beside the dense
  slot. The original key is
  always verified; stale, wrong-key, cross-cache, overlay, and post-rebuild
  handles recompute the ordinary exact route. The normal cache API remains
  adaptive and needs no configured maximum or hot set. A rare deleted-key
  prepared reinsertion uses the replacement-optimized boxed arena path until
  maintenance folds it back into the dense population.
- `get()` and `remove()` return a stable `CacheValue`. It owns an epoch guard,
  remains valid after replacement/removal, and is intentionally thread-local
  rather than `Send`.
- `insert_discard*()` and `remove_discard()` avoid retaining an old value and
  are the preferred cache-style mutation APIs.
- `replace_discard_with_options()` and its prepared variant update only a live
  key and never reinsert an absent one. Exact atomic index replacement returns
  the old arena handle, so replace-only and discard-removal paths retire it
  without a same-key mutex. This matches Papaya's update-only control rather
  than comparing an upsert against an update.
- `DirectCacheGuard::remove_discard()` uses a read-only absence check to keep
  delete misses off the mutation path. A successful exact index removal
  uniquely transfers the old handle's retirement responsibility, so discard
  removal can read its weight and queue it without entering a second reader
  epoch. Older readers remain protected.
- `DirectCacheGuard::removal_batch()` is an explicit delete-heavy scope. It
  retains one generation writer, uses an unconditional atomic swap for exact
  removal, batches 64 retired handles per sharded collector lock, and coalesces
  index-length decrements. Key absence, capacity, weight, and bounded-cache
  `len()` remain immediate. An unbounded cache's index-derived `len()` and
  removal statistics publish at each 512-delete refresh and scope drop. It owns
  one bounded 512-byte handle buffer per active scope; the ordinary guard path
  has no added state.
- `DirectCacheGuard::removal_batch_untracked()` compiles the same scope without
  removal-statistic publication. This is for services that already count
  requests outside the cache; capacity, weight, and reclamation stay exact.
- `insert_if_absent_with_options()` atomically preserves a racing cache-fill
  winner instead of overwriting it.
- `DirectCacheGuard::adaptive_admission()` creates a tiny caller-owned session
  for repeated conditional inserts. After two consecutive occupied results it
  uses an exact lock-free presence certificate; the first absent certificate
  disables that precheck and restores the ordinary new-key path. The two-hit
  threshold prevents alternating existing/new-key streams from continually
  predicting the wrong next operation. The lazy `*_by` form does not construct
  a value for a certified existing key. No adaptive state is added to the
  cache, resident entries, or ordinary read guard.
- A reusable direct guard already prevents generation cutover, so guarded
  conditional admission updates exact length accounting without separately
  registering and unregistering a writer for every key. Bounded caches defer
  successful length deltas in one guard-local scalar and publish one atomic
  update on refresh/drop instead of one per key. Single-item batches
  temporarily return to immediate accounting and periodically recheck.
- `DirectCacheGuard::admission_batch()` is the explicit pipeline API. Each
  successful insert updates entry/weight accounting immediately, while the
  limit check and eviction are coalesced. An adaptive entry window follows
  roughly twice the cache's proactive headroom, while a weight window follows
  0.1% of configured weight; long scopes therefore self-flush. Batch drop
  enforces any residual debt. Duplicate admissions retain the original value
  and do not add debt.
- `DirectCacheGuard::bulk_admission_batch()` is the explicit unbounded-loader
  variant. Keys and values publish immediately, but `len()` becomes exact only
  when the scope drops. Its local length accumulator adds no resident cache or
  per-entry bytes; bounded caches should normally use `admission_batch()`.

## Capacity, expiration, and eviction

- `max_weight` is mandatory and `max_entries` is optional.
- The default weight is `key.len() + size_of::<V>()`. Values owning heap memory
  need an explicit complete charge.
- Per-entry weight is limited to `u32::MAX`. This saves four bytes per value
  entry; larger charges return `WeightNotCompact`.
- Expiration uses 100 ms ticks and supports about 13.6 years from cache
  creation. A zero TTL expires immediately; nonzero TTLs round up to a tick.
- Compact CLOCK eviction uses one sampled access bit in the generation word.
  A hit marks approximately once per 16 reads. Eviction first chooses
  unaccessed entries and clears sampled bits for later passes.
- DirectPackedCache now follows Redis's constant-memory eviction shape: direct
  physical sampling from the adaptive atomic tables and dense frozen base feeds
  a bounded victim pool. Post-learning arbitrary-length keys now have native
  rotated bucket sampling; the small Papaya startup/emergency population is
  sampled proportionally in batches. Logical scans remain for expiration
  discovery and only when every physical sampler returns no candidate.
- Fallback refills copy candidate keys into one contiguous buffer. Retained
  candidates are split into 64-key chunks with one end offset per key, avoiding
  one heap allocation per sampled key while allowing consumed chunks to be
  released promptly.
- Every candidate still carries its exact arena handle. Removal revalidates
  that handle under the same-key mutation stripe, so a stale sample cannot
  delete a replacement value. The epoch pin predates sampling and retirement.
- Entry-only limits proactively create at most 0.1% headroom, capped by the
  configured eviction batch. This amortizes the maintenance gate. Scalar
  mutation calls return below the hard maximum; an explicit admission batch
  restores it when the batch is dropped. Weight-limited scalar calls retain
  exact one-at-a-time pressure because entry weights vary.
- Contending admission threads use non-queued maintenance ownership: losers
  wait only while the cache remains over limit instead of forming a mutex
  handoff convoy after another thread already created headroom.
- DirectPackedCache can opt into asynchronous eviction with
  `with_async_eviction(hard_limit_bps)`. Writers above the soft target coalesce
  wakeups to one registered maintenance worker; ordinary debt drains in the
  background, while writers crossing the hard-pressure threshold help drain
  synchronously. Strict synchronous enforcement remains the default.
- The hard threshold is backpressure rather than a transactional reservation:
  concurrent writers can each have one published admission in flight. The
  worker returns residency to the soft target, and stopping then restarting a
  worker safely replaces its wake registration.

## Memory result

Apple M4 Max requested-allocation measurements use one million mixed
8/16/24/32/48-byte binary keys and identical 64-byte inline values. Both sides
retain weight, expiry, and access metadata. The strongest Papaya control stores
the same compact `u32` weight, atomic `u32` expiry, one access bit, and value
directly inside its protected map node. This matches PackedGen's pinned
borrowed-read semantics without requiring a per-entry `Arc`. The older Arc
rows remain relevant when the consumer specifically requires independently
shareable owned values.

| Implementation | Requested B/entry | Allocations | Lower is better |
| --- | ---: | ---: | ---: |
| `DirectPackedCache<[u8; 64]>`, insert/replace API | **105.110** | 2,008,244 | **21.4% less than inline Papaya** |
| `DirectPackedCache<[u8; 64]>`, current guarded admission | **105.471** | **1,009,401** | 49.5% fewer allocations than inline Papaya |
| `PackedCache<[u8; 64]>` | 118.053 | 2,011,435 | 11.7% less than inline Papaya |
| Papaya inline compact CLOCK control | 133.693 | **2,000,006** | strongest pinned baseline |
| Papaya Arc compact CLOCK control | 157.693 | 3,000,006 | owned/shareable-value baseline |
| Papaya Arc timestamp-LRU control | 165.693 | 3,000,006 | practical richer metadata |

Subtracting the common 64-byte value gives 41.110 bytes of direct-cache
overhead, 54.053 bytes of generational-cache overhead, 69.693 bytes for inline
compact Papaya, 93.693 bytes for Arc compact Papaya, and 101.693 bytes for Arc
timestamp-LRU Papaya. DirectPackedCache reduces non-payload overhead by **41.0%
against the strongest inline control** and 56.1% against the Arc compact
control. It is not a 50% total cache reduction, because the value bytes
themselves cannot be compressed by a generic map.

The 118.053-byte result decomposes into the common 64-byte payload, about
33.074 bytes for the adaptive exact-key-to-`u64` index, and about 20.979 bytes
for the generational arena. The earlier approximately 30–33 B/entry adaptive
result was the complete key-to-`u64` map, not a cache containing an additional
64-byte value.

The implemented direct-pointer cache's insert/replace path measures 105.110
B/entry (105,109,832 live requested bytes): 12.943 B/entry
(11.0%) below the generational cache, or 24.0% less non-payload overhead. The
earlier standalone layout prototype measured 105.074. Conditional admission
and bulk load now use 256-entry epoch-recycled blocks. With the native
collector, sharded range directory, bounded adaptive fallback filter, and lazy
physical-pressure counters, native startup sample, and prepared route metadata,
that path is 105.471 B/entry and 1,009,401 allocations, 21.1% less requested
RAM and 49.5% fewer allocation calls than inline Papaya.
Known replacements retain boxed allocation because preserved-binary tests
found the system allocator's thread cache stronger for one-out/one-in churn.
The split arena is still experimental. The current safety suite contains an
exhaustive small-state Loom model for publication, replacement, removal,
reader entry, and three-epoch reclamation; nine focused Miri cases; all 38
ordinary direct-cache ASan tests; and ordinary plus prepared-recycler TSan
stress cases. Loom exposed and drove fixes for epoch-token ABA and a stale
maintenance-side reader-count observation. Pinned-Linux 24-hour endurance and
independent reproduction remain release gates.

After replacing every one of the one million values, PackedCache retains
118.074 B/live entry—only 0.021 B/entry above fresh state with the retained
512-object reclamation batch.

At 1,000 entries the current guarded-admission fixture uses 242,136 bytes,
down from 246,304 after making the 4 KiB physical-pressure counter bank lazy,
versus inline compact Papaya's 151,880. The adaptive index, native collector,
range directory, and partially occupied arena blocks have a startup cost, so
the large-cache density result must not be generalized to small caches.

Enabling `prepared-keys` without retaining handles measured 105.471 B/entry.
Retaining handles
for the hottest 1% costs 32,000 bytes at 200K entries, or 0.160 B/total entry.
The resulting effective 105.631 B/entry remains about 21.0% below the inline
Papaya control. Preparing every resident key would instead raise the effective
shape to about 121.471 B/entry and retain about a 9.1% density advantage. A
small adaptive hot set remains the intended policy because it preserves nearly
the full density lead and is cheaper to refresh after rebuild.

## Publication boundary

The library is worth publishing as experimental density-first cache research:

- the large-cache RAM reduction is now material and reproducible;
- exact binary keys, arbitrary values, multiwriter semantics, TTL, capacity,
  eviction, and stable values work end to end;
- reads are lock-free and write locking is partitioned, but the complete cache
  is not lock-free;
- the direct variant leads inline Papaya on replacement and read misses, and
  leads the Arc-valued control on read hit, miss, replacement, and the tracked
  mixed workload, but still materially trails inline Papaya on new-key
  admission and general read-heavy throughput; opt-in preparation can make a
  small stable hot set competitive without sacrificing density, while the
  eight-thread mixed hot-set row still trails; opt-in async eviction
  narrows but has not eliminated the at-capacity cache-mix gap;
- small caches do not receive the RAM win;
- rare fallback scans, maintenance ownership tails, and epoch reclamation still
  need production-grade latency analysis.

A retained admission reservation in `DirectCacheGuard` intentionally delays
generation cutover while guarded writers continue on that generation. The
ordinary read publication cache does not reserve a read batch: it validates
the authoritative current pointer on every lookup and refreshes a transitional
base before direct base mutation. Explicit guard refresh also advances arena
reclamation and releases any admission reservation. Long-running workers
should keep the documented periodic refresh; descheduled admission guards can
otherwise extend maintenance redirect latency.

The next gates are Linux CPU-pinned throughput and p99/p999 latency (including
async hard-threshold stalls), RSS and allocator comparisons, reclamation
stress under long-held guards, sanitizer coverage for the unsafe arena
boundary, and a formal publication/reclamation model. The four focused Miri
cases pass. Reproduce the focused churn
result with `cargo run --release --example cache_eviction_probe -- 10000 20000
21 64`, or the real pressure comparison with `cargo run --release --features
gxhash --example cache_probe -- 200000 10000000 8 11
cache_mix_95_pressure`.
The modified Elastic implementation is published as the explicitly owned
`packedgen-opthash` companion. `scripts/package_release.sh` verifies both crate
archives in dependency order; publish the companion before `packedgen`.
